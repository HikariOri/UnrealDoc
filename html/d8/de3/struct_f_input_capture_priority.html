◆ BINDING_COMPLEXITY_PRIORITY_STEP

int FInputCapturePriority::BINDING_COMPLEXITY_PRIORITY_STEP = 9
staticconstexpr

The binding complexity priority convention is a solution to the problem of ensuring the right behavior gets capture. Take the case of one behavior looking for LMB and another looking for Alt+LMB. If they have the same priority, which behavior gets capture is effectively non-deterministic. Priority would then need to be hand-tuned relative to each other, an inherently brittle task.

If all behaviors agree that that additional binding complexity increases capture priority by a set amount, all they must do is correctly publish their priority by this convention, and they will win out over less complex behaviors and gracefully lose to more complex behaviors.

An alternative discussed and discarded was to have behaviors assert their negative bindings. In this mode, a behavior wouldn't just look for LMB, it would look for LMB as well as NOT RMB, MMB, Ctrl, Alt, Shift, etc. This was rejected. Knowing how much to negatively assert is not well defined. Additionally, users often expect that pressing (for example) Alt+LMB will trigger an LMB action if nothing is bound to Alt+LMB.

The value of BINDING_COMPLEXITY_PRIORITY_STEP can be increased to give more wiggle room for nuanced behavior layering. As of writing, this number is intended such that DEFAULT_TOOL_PRIORITY - BINDING_COMPLEXITY_PRIORITY_STEP * 5 > DEFAULT_GIZMO_PRIORITY. The actual value should be considered experimental.
