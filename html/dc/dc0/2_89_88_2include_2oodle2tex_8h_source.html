112/* OodleTex_PixelFormat describes the format of the source pixel surface.
113
114 It is described by the number of channels, then the format of each channel.
115 For example, `OodleTex_PixelFormat_2_U16` is 32-bits per pixel, two 16-bit components, unsigned.
116
117 Multi-channel pixels listed in memory order and values are assumed to be normalized,
118 eg. `OodleTex_PixelFormat_4_U8_RGBA` is like `DXGI_FORMAT_R8G8B8A8_UNORM`, and `OodleTex_PixelFormat_2_S16`
119 corresponds to `DXGI_FORMAT_R16G16_SNORM`.
120
121 The pixel formats are treated as normalized (UNORM or SNORM) in the D3D convention. Opaque alpha is 255, 65535,
122 or 1.0, depending on format.
123
124 Float formats like `OodleTex_PixelFormat_4_F32_RGBA` can only be used with BC6 output. (The BC6 encoder requires
125 float input).
126
127 BC4S and BC5S (SNORM) can only be encoded from signed integer pixel formats (S8 or S16), all other formats will refuse
128 to read signed integer pixels.
129
130 The formats 1_F32 and 2_F32 cannot be directly encoded to BC4/5 but can be converted to S16 or U16 with
131 $OodleTex_BlitNormalized before encoding. They are included for convenience.
132
133 Formats without alpha act like they have an implicit opaque alpha channel (255 for `OodleTex_PixelFormat_3_U8_RGB`
134 and 1.0 for `OodleTex_PixelFormat_3_F32_RGB`). However, 3 channel RGB behaves differently than 4 channel RGBA with
135 opaque alpha in the RMSE call - with 3 channel it is assumed that "ignore alpha" was intended if not explicitly specified.
136 Similarly for the RGBx and BGRx formats: if they are promoted to RGBA, opaque alpha is set, but they are different
137 than RGBA in that they imply alpha should be ignored.
138
139 Oodle Texture does not need to know if the pixels are SRGB gamma corrected or not. Float input for BC6H is
140 assumed to be HDR linear light (unless BCNFlag_BC6_NonRGBData is specified).
141
142 See also $OodleTex_FAQ_ImageInputFormat and $OodleTex_MasteringGuide

284{
285 OodleTex_RDOLagrangeLambda_NearLossless = 1, // almost lossless (relative to baseline BCN)
286 OodleTex_RDOLagrangeLambda_VeryHighQuality = 10,
287 OodleTex_RDOLagrangeLambda_HighQuality = 20,
288 OodleTex_RDOLagrangeLambda_Default = 30,
289 OodleTex_RDOLagrangeLambda_MediumQuality = 40,
290 OodleTex_RDOLagrangeLambda_LowQuality = 60,
291 OodleTex_RDOLagrangeLambda_Min = 1,
292 OodleTex_RDOLagrangeLambda_Max = 100,
293 OodleTex_RDOLagrangeLambda_Force32 = 0x40000000
294} OodleTex_RDOLagrangeLambda;
295/* OodleTex_RDOLagrangeLambda provides reference values for the lagrange lambda parameter of OodleTex_EncodeBCN_RDO
296
297 Lambda tells the encoder how much you care about quality vs rate (compressed size) in $RateDistortionOptimization.
298
299 Lambda of zero you don't care about rate at all, and therefore get maximum quality (baseline BCN with no RDO).
300
301 Lambda of 1 (OodleTex_RDOLagrangeLambda_NearLossless) should almost always be used instead of zero,
302 as it will give you near-lossless quality (relative to baseline) but can sometimes find some nice rate savings.
303 In fact you can usually go to lambda 5 or 10 and still have super high quality. Do not treat lambda=1 as the
304 only near lossless option.
305
306 Higher lambdas correspond to more rate reduction and lower quality.
307
308 Lambda in 10-30 should be very small visual quality loss.
309
310 Lambda if 30-60 will have some apparent visual quality loss, but should be acceptable in most cases.
311
312 Lambda around 50 is the maximum you should use broadly without manual inspection of the results.
313
314 Lambda 50-100 can be used for further rate reduction, but is more unpredictable. It can give unacceptable
315 quality loss on some images, but is okay on others.
316
317 Lambda 30 is a good default starting point that will give a good balance of rate reduction and quality.
318
319 Lambda is not actually a quality parameter, and it can give different quality levels on different images.
320 This is intentional. Lambda is
321 more precisely an exchange rate between the different currencies of "rate" and "distortion". It tells our
322 codec how to value a decision, whether it is a profitable transaction to trade a certain rate improvement
323 for some distortion penalty. Higher lambda makes rate gains (size reduction) more value relative to a
324 given distortion penalty. See $RateDistortionOptimization
325
326 Any integer greater than zero can be used for lambda, not just the enumerated values. For example lambda of 5
327 will give results between OodleTex_RDOLagrangeLambda_NearLossless (1) and OodleTex_RDOLagrangeLambda_VeryHighQuality (10).
328
329*/

390 OodleTex_RDO_ErrorMetric_Default = 0, // Default is Perceptual
391 OodleTex_RDO_ErrorMetric_RMSE_RGBA = 1,

396/* Choose the way errors are scored in OodleTex_EncodeBCN_RDO.
397
398 This allows you to specify the "D" distortion metric used in the rate-distortion optimization.
399 Different distortion metrics will score errors in different ways, which changes the encoding.
400
401 Typically you should use the "Perceptual" metric. The Perceptual metric tries to preserve areas
402 where it thinks errors will be very visible to the human eye (such as in smooth gradients).
403 Perceptual tries to put more error where it thinks it will be hidden to the human eye, such as in
404 noisy or highly textured areas.
405
406 Perceptual is usually best on regular images, diffuse or albedo textures, or anything that will be
407 just looked at by the human eye without reintrepetation of the values.
408
409 The "RMSE" metric simply tries to minimize the squared error of all the channels. This can be useful
410 when the textures channels contain scalar fields which are not really an image. This is an option
411 when Perceptual gives undesirable results.
412
413 Note that when measuring codec performance using RMSE or related metrics such as PSNR, you should use
414 the RMSE metric, so that the codec is targeting the same goal you are measuring it by.
415
416 Default = Perceptual.
417
418 The difference between RGBA_Perceptual and RGB_A_Perceptual is whether the color and alpha channels
419 are treated separately or joint for purposes of visual masking. This only applies to BC3 and BC7 images
420 with alpha channels, in other cases they behave the same. When relevant, it determines whether noise in
421 color/alpha can mask the other. If A is storing a material property that should be treated separatey for
422 color, usually separating them by using RGB_A will be better.
423
424*/

426typedef enum OodleTex_RDO_UniversalTiling
427{
428 OodleTex_RDO_UniversalTiling_Disable = 0, // No universal tiling, the default. This option must be used when an $OodleTex_Layout is specified.
429 OodleTex_RDO_UniversalTiling_256KB = 1, // Universal tiling with 256KB blocks
430 OodleTex_RDO_UniversalTiling_64KB = 2, // Universal tiling with 64KB blocks
431 OodleTex_RDO_UniversalTiling_Max = 2,
432 OodleTex_RDO_UniversalTiling_Force32 = 0x40000000
433} OodleTex_RDO_UniversalTiling;
434/* Enables universal tiling, when desired.
435
436 Many platforms, especially game consoles, expose GPU-specific native image layouts that employ some kind
437 of texture tiling scheme. This can be targeted directly via $OodleTex_Layout, but this means that multi-platform
438 projects need to potentially do separate RDO texture encodes for every target.
439
440 The primary effect of native texture layouts as far as Oodle Texture is concerned is that large textures
441 usually end up being stored as a sequence of large rectangular 2D tiles, instead of scanline by scanline.
442 There is also reordering within those tiles but the effect on RDO encodes and compression performance is
443 relatively minor.
444
445 Universal tiling is a compromise: Oodle Texture internally processes a texture as individual tiles of the given
446 size. For example, 256KB universal tiling for BC7 textures treats a 2D square of 128x128 blocks as a unit.
447 However, both the input and output surfaces passed to Oodle Texture are still in the usual linear, row-major
448 order.
449
450 These textures can then be transformed into a number of platform-specific native orders and will in general
451 result in noticeably higher compression than if the texture had been encoded in the default linear order,
452 although generally somewhat worse than if the actual native $OodleTex_Layout had been used. Linear textures
453 using Universal Tiling will on average compress somewhat worse than regular linear layout textures on platforms
454 that store assets this way (e.g. PC or Mac), but not by much.
455
456 This makes it possible to cache a single RDO encode in universal tiling order and share the results between
457 multiple targets with different native texture tiling schemes, at a considerably saving in overall encode time.
458
459 In general, we've found 256KB block size to give the best overall trade-off across platforms, provided that
460 compression is done on independent chunks that are 256KB or larger (uncompressed). If you are paging and
461 decompressing data in smaller units, consider using the 64KB variant instead. See "$OodleTex_About_UniversalTiling"
462 in the "About" section of the documentation for more information.
463*/
