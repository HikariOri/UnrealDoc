89/*
90 * FVirtualizationManager
91 *
92 * Ini file setup:
93 *
94 * EnablePayloadVirtualization [bool]: When true the virtualization process will be enabled (usually when a package is submitted
95 to revision control. [Default=true]
96 * EnableCacheOnPull [bool]: When true payloads will be pushed to cached storage after being pulled from persistent
97 * storage. [Default=true]
98 * EnableCacheOnPush [bool]: When true payloads will be pushed to cached storage right before being pushed to persistent
99 * storage. [Default=true]
100 * MinPayloadLength [int64]: The minimum length (in bytes) that a payload must reach before it can be considered for
101 * virtualization. Use this to strike a balance between disk space and the number of smaller
102 payloads in your project being virtualized. [Default=0]
103 * BackendGraph [string]: The name of the backend graph to use. The default graph has no backends and effectively
104 disables the system. It is expected that a project will define the graph that it wants
105 and then set this option [Default=ContentVirtualizationBackendGraph_None]
106 * VirtualizationProcessTag [string]: The tag to be applied to any set of packages that have had the virtualization process run
107 * on them. Typically this means appending the tag to the description of a changelist of
108 * packages. This value can be set to an empty string. [Default="#virtualized"]
109 * AllowSubmitIfVirtualizationFailed [bool]: Revision control submits that trigger the virtualization system can either allow or block
110 * the submit if the virtualization process fails based on this value. True will allow a
111 * submit with an error to continue and false will block the submit. Note that by error we mean
112 * that the packages were not virtualized, not that bad data was produced. [Default=false]
113 * LazyInitConnections [bool]: When true, backends will not attempt to connect to their services until actually required.
114 * This can remove lengthy connection steps from the process init phase and then only connect
115 * if we actually need that service. Note that if this is true then the connection can come from
116 * any thread, so custom backend code will need to take that into account. [Default=false]
117 * DisableLazyInitIfInteractive [bool] When true 'LazyInitConnections' will be forced to false if slate is enabled. This exists because
118 * some backends can show slate dialogs when their initial connection fails to prompt for the
119 * correct login values. When 'LazyInitConnections' is true, this request can come on any thread and
120 * trying to marshal the slate request to the gamethread can often introduce thread locks. Setting
121 * both this and 'LazyInitConnections' to true will allow tools that do not use slate to initialize
122 * the VA connections on use, but force tools that can display the slate dialog to initialized
123 * during preinit on the game thread so that the dialog can be shown. Note that this only overrides
124 the setting of 'LazyInitConnections' via the config file, not cvar, cmdline or code [Default=false]
125 * UseLegacyErrorHandling [bool]: Controls how we deal with errors encountered when pulling payloads. When true a failed payload
126 * pull will return an error and allow the process to carry on (the original error handling logic)
127 * and when false a dialog will be displayed to the user warning them about the failed pull and
128 * prompting them to retry the pull or to quit the process. [Default=false]
129 * PullErrorAdditionalMsg [string] An additional message that will be added to the error dialog presented on payload pull failure.
130 * This allows you to add custom information, such as links to internal help docs without editing
131 * code. Note that this additional message only works with the error dialog and will do nothing
132 * if 'UseLegacyErrorHandling' is true. [Default=""]
133 * ForceCachingOnPull [bool]: When true backends will be told to always upload the payload when a caching as a result of
134 * a payload pull as in this scenario we already know that the backend failed to pull the payload
135 * before it was pulled from a backend later in the hierarchy. Can be used to try and skip
136 * expensive existence checks, or if a backend is in a bad state where it believes it has the payload
137 * but is unable to actually return the data. [Default=false]
138 * AllowBackendReconnection [bool]: When true backends that have previously failed to connect to their services can retry to connect
139 * each time they are accessed. When false the legacy behavior is invoked and backends may only attempt
140 * to connect a single time and after that will be unusable. [Default=true]
141 * UnattendedRetryCount [int32]: How many times the process should retry pulling payloads after a failure is encountered if the
142 process is unattended. Usually when a payload pull fails we ask the user to try and fix the issue
143 and retry, but in unattended mode we just log an error and terminate the process. In some cases
144 such as build machines with unreliable internet it is possible that the process could recover in
145 which case setting this value might help. Zero or negative values will disable the system.
146 Note: If many pulls are occurring at the same time on many threads a very short network outage might
147 spawn many errors in which case we try to group these errors into a single 'try' so 32 errors on 32
148 threads would not immediately blow past a retry count of 30 for example. [Default=0]
149 * UnattendedRetryTimer [int32] If 'UnattendedRetryCount' is set to a positive value then this value sets how long (in seconds)
150 * the process should wait after a failure is encountered before retrying the pull. Depending on the
151 likely cause of the failure you may want to set this value to several minutes. [Default=0]
152 */
