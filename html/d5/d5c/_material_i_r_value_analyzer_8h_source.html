17// It analyzes a value or instruction, performing semantic validation and side-effects execution.
18//
19// These analyze functions allow a value or instruction to perform non-trivial custom operations
20// and validation. These operations may have side effects, such as setting state in
21// CompilationOutput, allocating resources, etc. The reason these are done here (rather than at
22// FValue emission time) is that only values which are *actually* used (not pruned as unused or
23// optimized out) are analyzed. In other words, while implementing a value's analyze function, you
24// are guaranteed that the value is needed in the final material.
25//
26// Only values that require this kind of post-emission validation or that generate sidecar
27// resources should define Analyze functions. Otherwise, they can omit them.
28
29// There are two types of analyze functions: Analyze() and AnalyzeInStage().
30// - Analyze() is invoked once, regardless of which stage (vertex, pixel, or both) the value is
31// scheduled for. It runs before any per-stage logic.
32// - Some values require all or part of their analysis logic to run per stage. These should
33// implement AnalyzeInStage() with that stage-specific logic.
34//
35// IMPORTANT: Only give a value AnalyzeInStage() if it needs per-stage analysis. If the logic is
36// stage-agnostic, it belongs in Analyze(). A value can implement both Analyze() and
37// AnalyzeInStage() if it needs general logic once and other logic per stage.
38//
39// # GraphProperties
40// Analyze functions can set and read GraphProperty flags. These are per-value bitflags that are
41// automatically propagated as the IR graph is analyzed. When a value receives its Analyze() call,
42// all its dependencies have already been analyzed, so it can freely inspect their GraphProperties.
43// For example, it can verify that no other value sets a specific graph property upstream.
