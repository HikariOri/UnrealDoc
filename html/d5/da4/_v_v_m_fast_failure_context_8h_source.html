33 // The incoming effect token here is subtle. We allow things like <reads> in a fast failure
34 // context. They bump the effect token. If they suspend, they don't register with
35 // the fast failure context. So it won't even block the then/else of the fast failure context
36 // from running. The reason this is sound is we emit codegen in such a way that things like
37 // the RefGet unification will never fail. This isn't elegant, but it works.
38 // To have the then/else see a concrete effect token at *some point*, it means we are relying
39 // on things like the RefGet in a fast failure context to eventually run, even if the fast failure
40 // context has already failed. The reason they will continue to run today is because a RefGet
41 // suspension won't register with a fast failure context, only certain bytecodes do. So when it's
42 // leniently resumed, it doesn't ask if the fast failure context has already failed, it will just
43 // unconditionally run. If the MaxVerse checker proved that something like a RefGet didn't
44 // have to run for the program to be un-stuck, then this strategy wouldn't work, and we'd
45 // need to think of a way to capture the effect token incoming to the actual start of the if
46 // condition. We could probably do that by capturing that true incoming effect token as our
47 // initial leniency indicator until leniency is actually encountered.
48 // Given the above, this acts both as the incoming effect token to the then and the else.
49 VRestValue IncomingEffectToken{0};
50 // This is the effect token we unify with after running the then/else.
51 VRestValue DoneEffectToken{0};
